# Guía de entrevista · Ingesta Landing → Bronze (actividad 3.2)

## El pitch de 30 segundos

"Construí la ingesta a la capa Bronze. Carga 5 millones de filas tal como llegan, como texto, y le pone a cada fila su archivo de origen, el hash del archivo y la corrida que la cargó. Antes de cargar valida contra un manifiesto: que el archivo esté declarado, que su hash coincida y que traiga las filas esperadas. Es idempotente: si la corro dos veces no duplica nada, y si llega una versión corregida, reemplaza solo ese archivo. El mismo código corre sobre SQL Server y DuckDB, y en el CI lo pruebo contra un SQL Server 2022 real."

## Preguntas probables

**1. ¿Por qué guardas todo como texto en Bronze?**
Porque Bronze es la evidencia de lo que se recibió. Si tipifico al cargar, una fecha como "30 de febrero" o rompe la carga o se pierde en silencio. Dejo el dato intacto y lo detecto en Silver con una prueba, que queda registrada. Así puedo demostrar qué llegó, qué estaba mal y qué hice con ello.

**2. ¿Qué es la idempotencia y cómo la logras?**
Que correr el proceso una o diez veces dé el mismo resultado. Llevo un registro por archivo con su hash:
- **Mismo hash:** lo omito.
- **Mismo nombre con otro hash:** es una versión corregida. Borro las filas de ese archivo y cargo las nuevas, en una sola transacción con su registro de auditoría.

La primera corrida tarda un minuto y la segunda, menos de un segundo.

**3. ¿Para qué sirve el hash SHA-256?**
Es la huella digital del archivo: si cambia un solo carácter, cambia el hash. La prueba `test_archivo_alterado_se_rechaza` cambia un dígito en un archivo de saldos, y la ingesta lo rechaza sin detener a los demás archivos. En banca eso respalda la exactitud del reporte regulatorio: puedo probar que lo que reporté es lo que recibí.

**4. ¿Cómo rastreas una cifra de un tablero hasta su origen?**
Cada fila de Bronze tiene `meta_archivo`, `meta_fila`, `meta_sha256` y `meta_run_id`. De Gold bajo a Silver, de Silver a Bronze por la llave, y en Bronze sé el archivo, la línea exacta y la corrida. Esa corrida está en `audit.run_log` con el commit de Git que la ejecutó.

**5. ¿Qué pasa si un archivo llega tarde?**
Se carga, porque los datos son correctos, pero queda marcado como fuera del SLA de las 06:00. El monitor de cierre lo muestra en naranja. En los datos hay un caso real: las solicitudes de octubre llegaron a las 06:42.

**6. ¿Por qué dos motores, SQL Server y DuckDB?**
- **SQL Server** es el motor que usa la banca, y lo corro en mi equipo.
- **DuckDB** no requiere servidor, así que la corrida diaria pública en GitHub Actions es gratuita y demuestra que el sistema está en producción.

Separé la lógica del motor con un patrón de adaptador: la ingesta no sabe qué base usa.

**7. ¿Cómo probaste SQL Server sin exponer contraseñas?**
En el CI levanto un contenedor de SQL Server 2022 con una contraseña aleatoria que se genera en cada corrida y se enmascara en los logs. En mi equipo uso autenticación de Windows. No hay ninguna contraseña en el repositorio, y el escaneo de secretos con gitleaks lo verifica en cada pull request.

**8. ¿Qué harías si la fuente agrega una columna?**
La ingesta la detecta, agrega la columna a la tabla Bronze y la registra en `columnas_nuevas`. Es una señal de deriva de esquema, una de las cinco señales de observabilidad. Silver no la usa hasta que se decide qué hacer con ella.

## Términos que debes dominar

| Término | Explicación corta |
| --- | --- |
| Arquitectura Medallion | Capas Bronze (crudo), Silver (limpio) y Gold (listo para el negocio) |
| Linaje | Rastro de dónde viene cada dato y qué transformaciones tuvo |
| Idempotencia | Repetir una operación no cambia el resultado |
| Manifiesto | Lista de archivos entregados, con su hash y su conteo de filas |
| Deriva de esquema | La fuente cambia sus columnas sin avisar |
| Patrón de adaptador | Una interfaz común con varias implementaciones intercambiables |
| `fast_executemany` | Modo de pyodbc que envía lotes de filas en una sola llamada a SQL Server |
